# Архитектура

Laplace — платформа local-first веб-приложений. Пользовательские данные и логика приложений живут на
устройстве пользователя, а не на сервере; сервисы в сети — лишь опциональные источники данных и
точки встречи пиров.

```
   традиционная схема                       local-first схема

        Service ◄── персональные данные      Service      Service
        /     \                                 ┊   ╲      ┊
   Client     Client                       Client ┄┄┄┄┄┄ Client
                                          (данные)      (данные)
```

Приложения, которые исполняет Laplace, называются **лаппами** (lapp — Laplace application).

## Текущее устройство

```
┌──────────────────────────── laplace-app (процесс Tauri) ──────────────────────────────┐
│                                                                                       │
│  окно «laplace» (лаунчер)      окно «echo»                 окно «<lapp>»              │
│  ┌──────────────────────┐     ┌──────────────────────┐                                │
│  │ laplace-front (wasm) │     │ echo-front (wasm)    │     WebView на окно;           │
│  │ hypertext + wingy    │     │ htmx client-router   │     метка окна = имя лаппа     │
│  └─────────┬────────────┘     └─────────┬────────────┘                                │
│            │ invoke("open_lapp")         │ invoke("handle_http", Request)             │
│  ──────────┼─────────────────────────────┼──────────── Tauri IPC ─────────────────────│
│            ▼                             ▼                                            │
│   api::laplace::open_lapp       api::http::handle_http ── по метке окна ──┐           │
│   (WebviewWindowBuilder)                                                  ▼           │
│                                       State { lapps: LappsManager — реестр лаппов }   │
│                                                    │                                  │
│   FsStoredAssets ◄── lapp-<name>://… (ассеты окна) ▼ wasmtime (component model)       │
│   читает platform.frontend_assets_root      echo-back.wasm: export handler            │
│                                                                                       │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### Компоненты

| Крейт | Назначение |
| --- | --- |
| `laplace-app` (`crates/app`) | Хост: CLI, чтение `Laplace.toml`, логирование, `LappsManager` (wasmtime), Tauri-команды, раздача ассетов (`FsStoredAssets`), Android-обвязка |
| `laplace-settings` | Схемы `Laplace.toml` (`LaplaceSettings`), манифеста лаппа `manifest.toml` (`LappManifestSettings`), решений пользователя (`LappUserSettings`), разрешений и `UpdateQuery`. Общий для хоста и фронта: чтение и запись файлов и `config` — за feature `io`, которую включает только хост, так что без неё крейт собирается под `wasm32-unknown-unknown` |
| `laplace-common-api` | Сериализуемые `http::{Request, Response, Header}` — общий язык фронта и хоста |
| `laplace-front-api` | Обёртка над `window.__TAURI__.core.invoke` для wasm-фронтов (`handle_http`, `invoke`) |
| `laplace-front` | Лаунчер — UI самой платформы, лапп с именем `laplace` без back-части |
| `examples/echo/{back,front}` | Эталонный лапп |
| `wit/` | WIT-пакет `laplace:lapp@0.1.0`: `types`, `handler`, `lifecycle`, миры `back`/`back-init` (`worlds.wit`) |
| `webassets/vendor` | htmx, расширение `client-router`, стили wingy; раздаётся как псевдо-лапп `vendor` |

### Лапп = front + back

- **front** — модуль `wasm32-unknown-unknown` (`wasm-bindgen`), рисующий HTML через `hypertext` `rsx!` и
  компоненты `wingy-hypertext`. Интерактивность — htmx; расширение `client-router` перехватывает
  `htmx:configRequest` и отдаёт запрос wasm-функции `router`/`route`, а не в сеть.
- **back** — WASI-компонент (`cdylib` под `wasm32-wasip2`, обычный `cargo build`), исполняемый
  `wasmtime` внутри процесса хоста. Экспортирует `laplace:lapp/handler@0.1.0.handle(request) -> response`.
  Пишется на SDK `laplace-back-api` (`crates/back-api`): привязки `wit_bindgen::generate!` к миру
  `back-init` внутри SDK, трейт `Lapp` (`handle` на типах `http`, `init` с пустой реализацией),
  макрос `export!`, конверсия WIT ↔ `http` по правилам хоста и `Router` по методу и пути относительно
  `/<name>/api` (`404`/`405`, fallback). Back на SDK всегда экспортирует `lifecycle`; мир `back` —
  для back-ов без SDK. Обёртки над импортами этапов 3–5 тоже идут в SDK.
- Ни сокета, ни HTTP-сервера нет: фронт строит `laplace_common_api::http::Request`, вызывает команду
  `handle_http`, хост конвертирует запрос в WIT-типы и вызывает back лаппа, имя которого — метка окна.

### Путь запроса

1. Элемент с `hx-get="/echo/api/..."` → htmx → `client-router` → `wasm.router(path)`.
2. `router` → `laplace_front_api::http::handle_http(&Request)` → `invoke("handle_http")`.
3. `api::http::handle_http(webview_window, state, request)` берёт `webview_window.label()` и вне
   главного потока (`spawn_blocking`) отдаёт запрос `LappsManager::handle_http`: тот находит лапп в
   реестре, проверяет, что он включён, у него есть back и действует `invoke_back`, при первом
   запросе поднимает инстанс и зовёт `call_handle` под блокировкой этого лаппа.
4. Ответ back-а возвращается фронту; тот рендерит HTML-фрагмент, htmx вставляет его в DOM.

### Окна

`open_lapp(name)` отказывает лаппу, которого нет в реестре или который выключен, и строит
`WebviewWindowBuilder` с меткой `name`, URL `<name>/index.html` и заголовком — названием лаппа (из
решений пользователя, иначе из манифеста, иначе имя); уже открытый лапп поднимается, а не
открывается второй раз. Команда асинхронная: в синхронной команде сборка окна на Windows зависает.
На Android окно — activity: лаунчер — `MainActivity`, каждый лапп — `LappActivity` в отдельной задаче
(`documentLaunchMode="always"`).

Окно лаунчера создаётся из `Tauri.toml` с меткой `laplace`. Команды управления платформой
(`get_lapps`, `update_lapp`, `open_lapp`) первым делом вызывают `require_launcher` и отклоняют вызов
из любого другого окна; `handle_http` и `get_lang` доступны всем. Tauri ACL не используется: он
выбирает окна по той же метке, а команды с нелокального origin Tauri отклоняет и без него.

Каждое окно, и лаунчер тоже, открыто на своей схеме `lapp-<name>://localhost/<name>/index.html`
(`assets::lapp_url`). Отдельная схема даёт лаппу отдельный origin, а с ним и своё хранилище WebView,
на всех платформах: на Windows и Android своя схема превращается в `http://<схема>.localhost`, и
различить лаппы там может только схема — хост Tauri требует `localhost`, иначе считает origin
удалённым и отклоняет IPC. Схемы всех лаппов реестра и лаунчера регистрирует `start`; обработчик
(`FsStoredAssets::respond`) по метке окна из запроса отвечает только окну своего лаппа и только
`/<name>/**` и общими `/vendor/**`, ничего за пределами `frontend_assets_root`; всё прочее — `403`.
Встроенная схема `tauri://` не отдаёт ничего (`NoAssets`). Хук `on_web_resource_request` для этого не
годится: на Linux схемы регистрируются на общем `WebContext`, и `tauri://` получает хук первого окна —
лаунчера. Лапп, зарегистрированный после старта (этап 7), получит схему только после перезапуска,
если не регистрировать её через плагин во время работы. Переходы окна лаппа `on_navigation` пускает
только внутри его фронта — на своей схеме (в обеих формах) и по пути `/<name>/…`
(`assets::is_navigation_allowed`); ни в другой лапп, ни на внешний сайт окно не уходит. `window.open`
из окна лаппа запрещён (`on_new_window`): открытое так окно не было бы ни отфильтровано, ни привязано
к лаппу. Имена `laplace` и `vendor` зарезервированы платформой (`lapp::is_reserved`) и лаппам не
даются.

### Внешние запросы фронта

Каждый ответ схемы лаппа несёт `Content-Security-Policy` (`csp::policy`, `Lapp::csp`): перехватить
внешние запросы WebView можно только на WebView2 и Android, а CSP исполняют все движки, и код лаппа
ослабить политику из заголовка не может. По умолчанию фронт достаёт только свой origin (в обеих
формах) и IPC Tauri; `frame-src`, `object-src`, `form-action`, `base-uri` закрыты. Нужны
`'wasm-unsafe-eval'` (wasm-bindgen) и `'unsafe-inline'` в `style-src` (атрибуты `style` компонентов,
стили индикаторов htmx). Действующее право фронта `http` открывает в `connect-src` и `img-src`
`https://` действующие хосты фронта, `websocket` — `wss://` к ним же.

Хосты, как и права, манифест просит, а пользователь выбирает, и записываются они одинаково
(`LappSettings`): в манифесте — в `[required.…]`, в решениях пользователя — в `[allowed.…]`. Права —
`[required.permissions]` / `[allowed.permissions]` с `front` и `back`; хосты — отдельно для половин,
`[required.network.http.front] hosts` и `[required.network.http.back] hosts`, `methods`, `timeout_ms`
(методы и тайм-аут есть только у back-а: CSP их не ограничивает), а пользователь выбирает в
`[allowed.network.http.front] hosts` и `[allowed.network.http.back] hosts` хосты из манифеста или
`"all"` — все, что он просит. По умолчанию ничего не просится и не
разрешено. Действующие хосты (`LappUserSettings::effective_http_hosts`) — выбранные пользователем
хосты манифеста для половины, у которой есть действующее право `http`; если манифест просит `"all"`,
пользователь может разрешить и любые свои. Хост, похожий не на имя хоста, в политику не попадает, иначе манифест
дописал бы свои директивы. Методы `required.network.http.back.methods` CSP не ограничивает. Политика фиксируется при
загрузке страницы, поэтому `update_lapp` при выдаче или отзыве этих прав перезагружает открытое окно.

Cookie внешних сайтов в одном профиле WebView общие для всех лаппов с правом `http`: CSP этого не
меняет, а отдельного профиля на окно на Android нет. Поэтому фронтовое `http` — для открытых ресурсов;
запросы с сессией и cookie, а также с контролем методов, лапп делает через свой back.
CSP — фильтр движка, а не песочница: мелкие побочные каналы вроде DNS-prefetch он может не закрыть.

### Хранилище WebView

Профиль WebView у всех окон один (`data_directory` не задаётся), а хранилище разводит origin: у
каждого лаппа и у лаунчера своя схема (см. «Окна»). Отдельный профиль на лапп не нужен: хранилища
по origin в одном профиле и так раздельны, а на Android отдельного профиля на окно нет вовсе.

| | Linux (WebKitGTK) | Android | Windows | macOS |
| --- | --- | --- | --- | --- |
| `localStorage` раздельно по лаппам | да | да | не проверено | не проверено |
| IndexedDB раздельно по лаппам | да | да | не проверено | не проверено |
| `localStorage` и IndexedDB переживают перезапуск | да | да | не проверено | не проверено |
| cookie на своей схеме | не сохраняются (`document.cookie` после записи пуст) | сохраняются, другому лаппу не видны, в том числе с `Domain=localhost` | не проверено | не проверено |

Проверка — пробные значения из окна echo и их чтение из окна лаунчера, затем перезапуск
(`26-11-12 webview storage isolation.md`).

Для своих данных лаппы используют `localStorage` или IndexedDB. Cookie для этого не годятся: на своей
схеме их поведение зависит от движка (WebKitGTK их не хранит), а атрибут `Path` cookie не разделяет
лаппы — путь выбирает сам код лаппа (RFC 6265, §8.5–8.6). На Android и Windows origin имеет вид
`http://lapp-<name>.localhost`, там cookie хранятся по хосту, и на Android они другому лаппу не видны
даже с `Domain=localhost`; на Windows это не проверено.

Отдельный профиль на лапп (`data_directory` на Linux и Windows, `data_store_identifier` на macOS)
остаётся запасным вариантом — если проверка на какой-то платформе покажет общее хранилище, и для
cookie внешних сайтов, которые в одном профиле у всех лаппов общие (`26-11-13 front external http.md`).
Данные origin удалённого лаппа будет удалять `remove_lapp`.

### Раскладка на диске

```
Laplace.toml                        платформенный конфиг (на Android — Documents/Laplace/Laplace.toml)
lapps/back/<name>/manifest.toml     манифест лаппа; каталог есть у каждого лаппа
lapps/back/<name>/<name>-back.wasm  back лаппа, необязательный
lapps/front/<name>/index.html       фронт лаппа: webassets + dist/<name>-front{.js,_bg.wasm}
lapps/front/vendor/                 htmx, wingy
lapps/config/<name>.toml            решения пользователя о лаппе
lapps/data/<name>/                  каталог данных лаппа по умолчанию
```

Лапп разложен по четырём корням, и важно, кто их пишет:

| Корень | Настройка | Чей | Кто пишет |
| --- | --- | --- | --- |
| `lapps/back/<name>/` | `lapps.back_root` | автора | сборка, распаковка на Android, установка лаппа |
| `lapps/front/<name>/` | `platform.frontend_assets_root` | автора | то же |
| `lapps/config/<name>.toml` | `lapps.config_root` | пользователя | только хост, по решениям пользователя |
| `lapps/data/<name>/` | `lapps.data_root` | пользователя | лапп (через preopen) |

Корни автора заменяются целиком, корни пользователя этими операциями не трогаются никогда, так что
обновление лаппа не может ни выдать ему права, ни сбросить выданные. Решения пользователя лежат
отдельно от данных, потому что каталог данных целиком отдаётся лаппу. Каталог данных по умолчанию —
`data_root/<name>/`; пользователь может указать другой, а манифест — нет. Каталогов по версиям нет:
у имени один каталог в каждом корне.

Имя лаппа — `[a-z0-9-]`: оно одновременно имя каталога и файла, метка окна и (позже) хост origin.
Каталоги, имя которых начинается с `.`, служебные (замена при обновлении) и пропускаются молча.

На Android корни автора упакованы в APK как assets и распаковываются в каталог данных, корни
пользователя в пакет не входят (подробно — в `AGENTS.md`).

### Реестр лаппов

`LappsManager` (`crates/app/src/lapps.rs`) при старте читает для каждого каталога в `lapps.back_root`
манифест и решения пользователя (нет файла — начальные решения). Лапп с нечитаемым манифестом или
файлом решений пропускается с ошибкой в логе; значения по умолчанию вместо нечитаемого файла не
подставляются, чтобы следующая запись не затёрла файл пользователя. Лаунчер в реестр не входит: он
часть платформы, а не лапп с манифестом и решениями пользователя. Имя `laplace` за ним зарезервировано
— каталог с таким именем в `lapps.back_root` пропускается, а окно с этой меткой — окно лаунчера.

Инстансы отделены от реестра: при старте поднимаются только включённые лаппы с `autoload`, остальные —
при первом запросе. Back компилируется и линкуется один раз на лапп (`Lapp::compiled`, `HttpPre`),
перезапуск инстанса — только новый `Store`; `Linker` с WASI общий для всех лаппов.

Вызов back-а ограничен дедлайном `lapps.call_timeout_ms` (по умолчанию 10 с): `Engine` прерывает
код по эпохам, тикер продвигает эпоху раз в 10 мс, перед каждым вызовом `Store` получает свой
дедлайн. Память инстанса ограничена `lapps.memory_limit_mb` (по умолчанию 256 МБ, `StoreLimits`):
`memory.grow` сверх лимита не выделяет память, и back падает сам. После любого trap инстанс
отбрасывается — в компонент после trap повторно не входят, — и следующий запрос поднимает новый из
скомпилированного back-а; истёкший дедлайн — `LappError::Timeout`. Блокирующие вызовы хоста (сон
WASI, а на этапе 3.3 ожидание сети) дедлайн по эпохам не прерывает: их ограничивают свои тайм-ауты
хоста. Мапа реестра после старта не меняется, а у каждого лаппа своя блокировка инстанса, так что
компиляция компонента одного лаппа не задерживает запросы к другим.

Вывод back-а идёт в лог хоста (`wasi::output::LogOutput`): цель `lapp::<name>`, stdout — `info`,
stderr — `warn`, одна запись на строку, так что вывод лаппа включается и выключается в `log.spec`
(`lapp::echo=debug`, `lapp=warn`) и на Android попадает в logcat под тегом `Laplace`. Хвост без
перевода строки хост дописывает после каждого вызова и при сбросе инстанса — но только то, что до
хоста дошло: stdout Rust буферизует построчно в самом back-е, и `print!` без перевода строки до
следующего `\n` хост не видит. Строка длиннее 4 КиБ обрезается с пометкой `[truncated]`; частота
записей не ограничена. Сообщение паники back-а попадает в лог перед ошибкой вызова.

Контракт back-а — WIT-пакет `laplace:lapp@0.1.0` (`wit/`). Версия входит в имена экспортов
(`laplace:lapp/handler@0.1.0`), а сопоставления экспортов по semver в wasmtime нет: до 1.0 любая смена
версии пакета ломает собранные back-и. Хост при компиляции проверяет экспорт `handler` нужной версии
и отказывает back-у другого контракта понятной ошибкой `LappError::Start`. Импорты возможностей
(этапы 3–5) объявляются в мире `back` все; собранный компонент сохраняет только те, что вызывает его
код (проверено: импорт мира, который echo не вызывает, в `echo-back.wasm` не попадает), а хост
линкует все.

Back может экспортировать необязательный `laplace:lapp/lifecycle@0.1.0.init(previous-version)` —
для этого он собирается на мире `back-init`, остальные остаются на `back`. Хост находит экспорт
при компиляции и вызывает `init` на каждом новом инстансе до первого запроса, под тем же дедлайном и
лимитом памяти, поэтому `init` должен быть идемпотентным. `previous-version` — `application.version`
из решений пользователя, если она не пустая и не равна версии манифеста; после успешного запуска (с
`init` или без) хост записывает туда версию манифеста — так лапп после обновления узнаёт, с какой
версии переводить данные (этап 7). Отказ `init` — `LappError::Init`: инстанс не сохраняется, версия не
записывается, следующий запрос пробует снова.

Лаунчер получает реестр командой `get_lapps` (`LappInfo`: манифест, решения пользователя, действующие
права, запущен ли back) и меняет решения пользователя командой `update_lapp(UpdateQuery)`. Изменение
делается в копии и записывается в `lapps/config/<name>.toml`, а в реестр попадает, только если запись
удалась. Выключение и выдача или отзыв права останавливают работающий back; следующий поднимается при
первом запросе. Смена `autoload` инстанс не трогает.

## Чем это отличается от прежних реализаций

Прежний Laplace (`../old/laplace`) был HTTP-сервером: лаппы открывались в обычном браузере.
Промежуточная версия (`../old/laplace-new-old`) — первый прототип на Tauri, функционально почти
совпадающий с текущим кодом (текущий — его доработка).

| Аспект | Прежний `laplace_server` | Текущий `laplace-app` |
| --- | --- | --- |
| Оболочка | axum-сервер (HTTP/HTTPS, self-signed TLS) + браузер пользователя | Tauri 2, своё окно на лапп, Android-пакет |
| Доступ | access token в cookie на путь лаппа | процесс локальный, сети нет; разграничение — по метке окна: команды управления принимаются только от окна `laplace` |
| Back | core-модуль wasm, ручное ABI: `alloc`/`dealloc`, `WasmSlice`, borsh, макрос `#[http::process]` | WASI-компонент, WIT-мир, `wasmtime::component::bindgen!` / SDK `laplace-back-api` на `wit-bindgen` |
| Исполнение | поток на лапп, актор `LappService` (`truba`), async wasmtime, ленивый запуск + `autoload` | реестр + ленивый запуск и `autoload`, блокировка на лапп, вызов в `spawn_blocking` |
| Возможности back-а | FS (preopen `data_dir`), SQLite, исходящий HTTP (reqwest, фильтр методов/хостов), sleep — по разрешениям | только WASI без preopen |
| Push к клиенту | WebSocket ↔ `route_ws` | нет |
| P2P | libp2p gossipsub + mDNS, `route_gossipsub` | нет (только настройки) |
| UI платформы | Yew + MDC: список, вкл/выкл, autoload, разрешения, загрузка `.lar`, ошибки | hypertext + wingy + htmx: захардкоженный список из одного лаппа, кнопка «открыть» |
| Фронт лаппов | Yew-приложения со своим `index.html` в `static/` | hypertext + wingy + htmx, клиентский роутинг |
| Раскладка | `lapps/<name>/{config.toml, <name>_server.wasm, static/, data/}` | четыре корня: `lapps/{back,front}/<name>/` автора, `lapps/config/<name>.toml` и `lapps/data/<name>/` пользователя |
| Тесты | интеграционные: запуск сервера, проверка доступа по HTTP | нет |

## Целевая архитектура

Направление, в котором ведёт план миграции (`26-10-01 migration plan.md`):

- **Реестр лаппов** отдельно от **исполнения**: хост читает манифесты всех лаппов, а инстанс back-а
  поднимает лениво или при старте (`autoload`), только для включённых.
- **Исполнитель на лапп**: каждый инстанс в своём потоке/задаче с очередью сообщений (аналог
  `LappService`), с таймаутом вызова (epoch interruption) и лимитами памяти; паника или trap
  лаппа не роняет платформу.
- **Возможности back-а — WIT-импорты**, линкуемые только при выданном разрешении: файловая система
  (preopen каталога данных), база данных, исходящий HTTP (`wasi:http` с фильтром), push во фронт,
  P2P. Back экспортирует обработчики: `handle` для запросов фронта, обработчики входящих сообщений
  и инициализацию.
- **Push вместо WebSocket**: события/каналы Tauri в окно лаппа.
- **Разграничение доступа по окну**: команды управления платформой доступны только окну
  `laplace`, лапп видит только свои ассеты и свой back.
- **Установка лаппов** из архива `.lar` без перезапуска платформы.
