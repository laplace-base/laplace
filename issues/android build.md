Как можно убрать дублирование фронтенда в APK? Только ответь, ничего не меняй.

---

● Дублирование берётся из одного места: frontend-dist = "../../lapps/front/" в crates/app/Tauri.toml — tauri::generate_context!() вшивает весь этот каталог в бинарник на этапе компиляции, а в рантайме и
  run_desktop, и run_mobile вызывают context.set_assets(FsStoredAssets), то есть вшитая копия никогда не читается. Плюс те же файлы едут ассетами пакета.
  
  Самый прямой способ — сделать frontend-dist заглушкой. Тауривский контекст всё равно нужен только как контейнер, поэтому вместо lapps/front можно указать на закоммиченный каталог с одним пустым index.html
  (например crates/app/webassets-stub, путь в Tauri.toml относителен самому Tauri.toml). Вшитыми останутся десятки байт вместо ~600 КБ, и это уберёт копию и на десктопе тоже. Проверить нужно две вещи:
  tauri-build требует, чтобы каталог существовал (пустой путь или несуществующий — ошибка сборки), и CLI ругается, если в dist нет index.html. Если хочется оставить вшитые ассеты на десктопе, Tauri 2 умеет
  платформенные оверрайды конфига — Tauri.android.toml рядом с Tauri.toml мержится поверх основного при сборке под Android, туда и можно положить заглушечный frontend-dist.
  
  Вариант «наоборот» — не паковать фронтенды ассетами, а вернуться к вшитым: на Android не звать set_assets и распаковывать только Laplace.toml и lapps/back. Дублирования тоже нет, но теряется главное, ради
  чего всё затевалось: единый путь с десктопом и возможность посмотреть/подменить фронтенд файлом на устройстве.
  
  Вариант без копий вообще — свой Assets, читающий прямо из APK: получить AAssetManager через AAssetManager_fromJava (или те же JNI-вызовы, что уже есть в android.rs) и отдавать байты из AAsset в Assets::get,
  iter() строить через AssetManager.list. Тогда фронтенд не копируется ни в бинарник (вместе с заглушкой из первого пункта), ни во внешнее хранилище, и старт становится быстрее. Бэкенды при этом тоже можно
  грузить прямо из ассетов — Component::from_binary принимает байты, — но тогда во внешнем хранилище не останется ничего, и лаппам негде будет держать свои данные, так что распаковку lapps/back я бы оставил.
  
  Одно уточнение по масштабу: это вопрос чистоты, а не размера. Дубль — примерно 600 КБ из 194 МБ APK; вес дают четыре ABI с wasmtime внутри. Если цель именно размер, работают --split-per-abi или сборка под
  нужные таргеты (--target aarch64 --target x86_64), а не устранение дубля.

Не нужно ли разрешить андроид приложению читать и писать во внешнее хранилище, чтобы можно было теперь загружать и сохранять оттуда файлы?

---

● Нет — для того, что приложение делает сейчас, ничего добавлять не нужно, и это уже подтверждено: в манифесте нет ни одного разрешения на хранилище, а распаковка в /sdcard/Android/data/org.laplace/files/data
  на Android 31 отработала. Каталог из getExternalFilesDir() — это app-specific часть внешнего хранилища, доступ к ней не требует разрешений начиная с API 19 (у нас minSdk = 24), и READ/WRITE_EXTERNAL_STORAGE
  там не дали бы ничего. Побочные свойства этого каталога: он стирается при удалении приложения и на Android 11+ не виден большинству файловых менеджеров (через adb shell — виден, как мы и смотрели).
  
  Разрешения понадобятся только если файлы нужно читать/писать за пределами своей песочницы — в общих Downloads, Documents, на «корне» карты. И тут расклад такой:
  
  - Android 6–10: READ_EXTERNAL_STORAGE / WRITE_EXTERNAL_STORAGE в манифесте плюс запрос в рантайме.
  - Android 11+ (API 30+): WRITE_EXTERNAL_STORAGE игнорируется, requestLegacyExternalStorage больше не работает. Широкий доступ даёт только MANAGE_EXTERNAL_STORAGE («All files access»), а его Google Play
    пропускает лишь файловым менеджерам и бэкап-приложениям по отдельной заявке — для Laplace это плохая ставка.
  - Медиа на API 33+: READ_MEDIA_IMAGES/VIDEO/AUDIO, либо Photo Picker вообще без разрешений.
  
  Штатный путь для «открыть/сохранить файл» на современных Android — это Storage Access Framework: ACTION_OPEN_DOCUMENT, ACTION_CREATE_DOCUMENT, ACTION_OPEN_DOCUMENT_TREE. Разрешений он не требует вовсе, доступ
  выдаёт сам пользователь при выборе файла или папки, и его можно сделать постоянным через persistable URI permissions. В терминах Tauri это tauri-plugin-dialog + tauri-plugin-fs (сейчас в проекте подключены
  только opener и shell), их андроидная реализация как раз ходит через SAF и content://.
  
  Два подводных камня, которые важнее самих разрешений. Первый: SAF отдаёт content://-URI, а не путь — std::fs его не откроет, читать/писать придётся через API плагина (или через ContentResolver по JNI, как в
  android.rs). Второй, и он тут главный: у лаппов сейчас файлового доступа нет вообще независимо от Android — WasiStates не даёт компоненту ни одного preopen-каталога, а хост-команд для файлов, кроме
  handle_http, нет. То есть «загружать и сохранять файлы» упирается не в манифест, а в отсутствующее API между лаппом и хостом; когда оно появится, на Android его естественно будет завести именно на SAF, и
  манифест по-прежнему останется без разрешений на хранилище.
  
  Отдельно, если задумка была «пользователь кладёт файл в папку, приложение его подхватывает»: на Android 11+ положить что-то в Android/data/org.laplace/files с телефона обычным файловым менеджером не выйдет.
  Тогда обмен придётся делать либо через SAF-папку, выбранную пользователем, либо через публичный Documents/Laplace (MediaStore), а не через текущий каталог распаковки.

● Коротко: да, пользователь может выдать Laplace полный доступ ко внешнему хранилищу — это MANAGE_EXTERNAL_STORAGE («Доступ ко всем файлам»), — и именно оно делает вашу схему с собственной системой
  разграничения доступа реализуемой. А каталог для лаппов при этом лучше вынести в общее хранилище, например Documents/Laplace/.

  Каталог

  Android/data/org.laplace/files не подходит по обоим вашим критериям: он стирается при удалении приложения и на Android 11+ не виден ни другим приложениям, ни файловым менеджерам. Нужен каталог на общем томе —
  он переживает удаление приложения (система чистит только app-specific каталоги), виден по MTP через USB, доступен из файловых менеджеров и выбирается через SAF.
  
  Из двух вариантов — /sdcard/Laplace/ и /sdcard/Documents/Laplace/ — я бы взял второй. Разница практическая: создать свой каталог в корне тома можно только имея уже выданный MANAGE_EXTERNAL_STORAGE, а внутрь
  Documents приложение может писать и без него, через MediaStore с RELATIVE_PATH = "Documents/Laplace". То есть на Documents/Laplace можно опереться и в том состоянии, когда пользователь разрешение ещё не дал.
  Плюс Documents — стандартная коллекция, её индексирует MediaStore, поэтому содержимое сразу видно по MTP (после записи по обычному пути имеет смысл дёргать MediaScannerConnection.scanFile, иначе файл появится
  в индексе не сразу).
  
  «Доступен для записи внешним приложениям» тут значит ровно то, что может дать Android: писать туда сможет пользователь (файловый менеджер, ПК по USB) и приложения, у которых либо есть свой широкий доступ,
  либо пользователь выдал им SAF-доступ на эту папку. Отдельного «сделать папку публично-записываемой» в Android нет — POSIX-права на общем томе эмулируются и не настраиваются.

  Полный доступ                                                                            
                                                                                           
  MANAGE_EXTERNAL_STORAGE (API 30+) — не runtime-разрешение, обычным диалогом его не запросить:
                                                                                           
  - в манифест — <uses-permission android:name="android.permission.MANAGE_EXTERNAL_STORAGE" />;
  - на старте проверять Environment.isExternalStorageManager();                            
  - если нет — отправлять пользователя интентом ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION с package:org.laplace в системные настройки, где он переключает тумблер.

  Что это даёт: чтение и запись всего общего хранилища обычными путями — то есть работает std::fs, а значит и preopened_dir у wasmtime. Именно это принципиально: лаппы у вас исполняются как WASI-компоненты, и
  выдавать им доступ естественно через preopen-каталоги, а preopen требует настоящего пути.

  Чего это не даёт даже с выданным разрешением: чужих Android/data/<pkg> и Android/obb/<pkg>, внутренних данных других приложений (/data/data/...) и всего, что вне общих томов. Так что «доступ ко всему» на
  Android — это «ко всему пользовательскому хранилищу», не к системе. Разрешение пользователь может в любой момент отозвать, а спящие приложения система умеет сбрасывать, поэтому проверять
  isExternalStorageManager() надо на каждом старте, а не один раз при установке.

  Для API 24–29 нужна отдельная ветка лестницы: READ_EXTERNAL_STORAGE/WRITE_EXTERNAL_STORAGE (второе с android:maxSdkVersion="29") плюс runtime-запрос, а на API 29 ещё
  android:requestLegacyExternalStorage="true", иначе там включится scoped storage.

  Ограничение, о котором стоит знать заранее

  Google Play пускает MANAGE_EXTERNAL_STORAGE только для приложений, чья основная функция — работа с файлами: файловые менеджеры, бэкап, антивирусы, документооборот. Нужна отдельная декларация в консоли, и
  «платформа для запуска приложений» — не гарантированно проходящая формулировка. При распространении сайдлоадом или через F-Droid вопрос не стоит вовсе.
  
  План Б на случай Play — ACTION_OPEN_DOCUMENT_TREE: пользователь сам выбирает корень (в 11+ нельзя выбрать корень основного тома, Download и Android/data, но Documents/Laplace — можно), доступ делается
  persistable и переживает перезагрузку и обновление, но не переустановку. Цена: всё превращается в content://, std::fs их не открывает, и под WASI пришлось бы писать собственную реализацию wasi:filesystem
  поверх ContentResolver вместо cap-std — это заметно больше работы, чем preopen реального каталога. Разумный компромисс — поддержать оба режима: по путям, когда «Доступ ко всем файлам» выдан, и через
  SAF-дерево, когда нет. 
  
  Что из этого следует для нынешнего кода
  
  Как только каталог лаппов переезжает в общее хранилище и переживает удаление приложения, текущая политика распаковки «всегда перезаписывать, ничего не удалять» становится неверной: она затрёт то, что
  пользователь или лапп там поменяли. Нужен либо маркер версии на лапп (распаковывать из APK только при отсутствии или при росте версии), либо копирование только недостающего. Туда же логично переехать и
  Laplace.toml — тогда его можно править с телефона, не пересобирая APK. И имеет смысл сохранить fallback на нынешний getExternalFilesDir(), чтобы приложение оставалось работоспособным, пока разрешение не
  выдано.
