# Разница

## `../old/laplace-new-old`

Это первый прототип на Tauri, и текущий проект — его прямое продолжение: `laplace-app`,
`laplace-settings`, `laplace-common-api`, `laplace-front-api`, `wit/http.wit` и echo перенесены почти
дословно (с тех пор добавлены `FsStoredAssets`, Android-обвязка, окно на лапп). Не перенесено:

- `laplace-core` — побайтовая копия `laplace_common` из старого Laplace: `UpdateQuery`/`UpdateRequest`
  и ответ `Lapps | Updated` (API настроек лаппа, с тестами сериализации), `Peer`, хелперы `Lapp`
  (`main_name() == "laplace"`, пути). Нужно при переносе управления лаппами (этап 1.3);
- UI лаунчера на leptos + thaw: боковая панель «Настройки», переключатель «включён», чекбокс
  «автозагрузка», выбор разрешений (`TagPicker`), локализация en/ru (`locales/*.json`) с меню
  смены языка через команду `get_lang`. Всё это без связи с хостом, на захардкоженных данных, но это
  готовый макет для этапа 6;
- `capabilities/default.json` (в текущем каталога `capabilities` нет вовсе);
- Android-код (`copy_all_assets`) устарел и заменён текущей распаковкой.

## `../old/laplace`

Полноценная прежняя реализация — HTTP-сервер на axum, лаппы в браузере. По подсистемам:

Попутно найдено в текущем коде:

- `handle_http` — синхронная Tauri-команда, а такие выполняются в главном потоке: долгий вызов back-а
  замораживает все окна. Все лаппы к тому же сериализованы одним `Mutex`;
- `handle_http`, `load_lapps`, `LappState::new` паникуют на любой ошибке; один битый `.wasm` не даёт
  запуститься платформе;
- все окна получают все команды (`open_lapp`, `handle_http`, будущие команды управления) и все ассеты
  из `frontend_assets_root` — лапп может загрузить чужой фронт; все окна на одном origin, т.е.
  делят `localStorage`/IndexedDB;
- `examples/echo/config.toml` описывает `[permissions.front]`/`[permissions.back]` с `invoke_back`,
  а `PermissionsSettings` ждёт плоские `required`/`allowed` — при чтении секции молча станут пустыми;
- обработчик схемы `app://` — мёртвый код (см. `NOTES.md`); `tauri-plugin-opener` подключён в
  зависимостях, но не используется; `tauri-plugin-shell` инициализируется, но без capabilities его
  команды недоступны.

# План

Этапы упорядочены по зависимостям; внутри этапа шаги можно делать отдельными задачами. Для каждого
шага — что сделать и как понять, что сделано.

## Этап 0. Устойчивость хоста

0.1. **Ошибки вместо паник.** `handle_http` возвращает `Result<Response, String>` (или
сериализуемую ошибку); `load_lapps` пропускает лапп, который не загрузился, с `log::error!`.
Готово: битый `.wasm` в `lapps/back/` не мешает старту, запрос к нему возвращает ошибку во фронт.

0.2. **Не блокировать главный поток.** `handle_http` — `async`-команда, вызов back-а через
`tauri::async_runtime::spawn_blocking` (до этапа 2.1, где появится исполнитель на лапп).
Готово: back с бесконечным циклом не замораживает лаунчер.

0.3. **Уборка.** Удалить обработчик `app://` (или переиспользовать в 1.7), убрать неиспользуемый
`tauri-plugin-opener`; для `tauri-plugin-shell` — либо capabilities, либо удалить.

0.4. **Каркас тестов.** Тест-хелпер, который собирает/находит `echo-back.wasm` и прогоняет
`LappState` без Tauri; `cargo make test` собирает компоненты до тестов, CI ставит `cargo-component`
и `wasm32-wasip1`. Готово: в CI зелёный тест «echo отвечает на GET».

## Этап 1. Манифест, реестр, разграничение доступа

1.1. **Раскладка лаппа.** Решить, где лежит манифест. Предложение: домашний каталог лаппа —
`lapps.path/<name>/` (сейчас `lapps/back/<name>/`): `config.toml`, необязательный
`<name>-back.wasm`, `data/`; фронт остаётся в `frontend_assets_root/<name>/` (раздельные корни —
решение из TODO `laplace-new-old`). `deploy-back` в `Makefile.toml` копирует `config.toml`;
`android-assets` подхватывает его автоматически. Лапп без back-а (лаунчер) получает манифест так же.

1.2. **Модель разрешений.** Выбрать: плоский список (как в старом, `client_http` вместо
`invoke_back`) или раздельные `front`/`back`. Плоский проще и совместим со старыми манифестами;
привести `examples/echo/config.toml` к выбранному виду и добавить тест разбора манифеста.

1.3. **Чтение и запись манифестов.** Перенести в `laplace-settings` из старого `FileSettings`
(`load`/`save`/`update` через `toml`), `UpdateQuery` с тестами из `laplace_common/src/api/update.rs`,
`is_lapp_startup_active`, константу `main_name = "laplace"`.

1.4. **Реестр отдельно от инстансов.** `LappsManager` хранит `LappSettings` всех лаппов и, отдельно,
работающие инстансы. Инстанс создаётся при старте для `enabled && autoload`, остальные — при первом
`handle_http`. Перед вызовом — проверка `enabled` и разрешения `client_http`
(аналог `check_enabled_and_allow_permissions`). Готово: выключенный лапп отвечает ошибкой,
лапп без `autoload` грузится при первом запросе.

1.5. **Команды лаунчера.** `get_lapps() -> Vec<LappSettings>` (без самого `laplace`, сортировка по
имени), `update_lapp(UpdateQuery) -> UpdateQuery` с сохранением в `config.toml` и перезапуском
работающего инстанса при изменении (как `update_lapp_settings`). `open_lapp` отказывает
выключенному лаппу.

1.6. **Команды — только своим окнам.** Команды управления принимаются только от окна с меткой
`laplace` (проверка `webview_window.label()`, плюс Tauri ACL: `capabilities/` с окнами и
`tauri_build::AppManifest::commands`, чтобы на команды приложения действовали права). Окна лаппов
получают только `handle_http` и `get_lang`. Готово: тест на mock-рантайме `tauri::test` — вызов
`get_lapps` из окна `echo` отклоняется.

1.7. **Ассеты — только свои.** Окну лаппа отдаются только `/<name>/**` и `/vendor/**` (+ каталоги из
`additional_static_dirs`, их использовал notes). `Assets` не знает окна, поэтому нужна своя схема
через `register_uri_scheme_protocol` с проверкой `ctx.webview_label()` и `WebviewUrl::CustomProtocol`
в `open_lapp` и для главного окна.

1.8. **Изоляция хранилища WebView** (исследование): у всех окон сейчас общий origin. Варианты —
origin на лапп (хост в URL схемы; проверить поведение на Windows/Android, где кастомные схемы
отображаются в `http://<scheme>.localhost`), `data_directory`/`data_store_identifier` для окна.
Результат — решение, записанное в `docs/architecture.md`.

## Этап 2. Исполнение back-ов

2.1. **Исполнитель на лапп.** Каждый инстанс — в своём потоке (или tokio-задаче) с очередью
сообщений, как `LappService` из старого: `Http(request, oneshot)`, `Stop`, позже — входящие
push/P2P-сообщения. `State` хранит отправители, а не `Store`. Общий `Engine`, компиляция
`Component` и `Linker`/`InstancePre` — один раз на лапп. Готово: два лаппа обрабатывают запросы
параллельно; `Stop` освобождает инстанс.

2.2. **Таймауты и лимиты.** `Config::epoch_interruption` + тикер эпох и дедлайн на вызов (значение в
`Laplace.toml`), `StoreLimits` на память. Trap или паника → ошибка в ответе и пересоздание инстанса
при следующем запросе (старый TODO.log: «паника в серверном wasm = завершение работы»).

2.3. **Инициализация.** Необязательный экспорт `init: func() -> result<_, string>` (todo создавал в
нём таблицу), вызывается один раз после инстанцирования; ошибка делает лапп недоступным с
понятным сообщением.

2.4. **Логи back-а.** stdout/stderr WASI → `log` хоста с целью `lapp::<name>` (кастомные
`StdoutStream` в `WasiCtxBuilder`).

2.5. **WIT-мир лаппа.** Переименовать/версионировать пакет (`laplace:lapp@0.1.0`): интерфейс типов,
экспорт `by-client-handler`, `init` и (на этапах 3–5) импорты возможностей хоста. Хост генерирует
привязки на весь мир, а мир собирается из интерфейсов, чтобы back, которому не нужен импорт, его не
импортировал.

2.6. **SDK для back-ов** — замена `laplace_wasm`/`laplace_wasm_macro`: крейт `laplace-back-api`
с привязками `wit-bindgen` (`generate!` с `pub_export_macro`, чтобы лаппы не генерировали свои
`bindings.rs`), конверсией в/из типов `http`, роутингом по пути и обёртками над импортами
(`database::query`, …). Echo переводится на SDK.

## Этап 3. Возможности хоста по разрешениям

Импорты линкуются только при выданном разрешении — как в старом `Lapp::instantiate`, где
`func_wrap` делался только для разрешённого. Без разрешения back с таким импортом не инстанцируется,
и это видно в лаунчере.

3.1. **Файлы** (`file_read`/`file_write`): `WasiCtxBuilder::preopened_dir(data_dir, "/", DirPerms,
FilePerms)`, создание `data_dir`, относительный путь — от домашнего каталога лаппа. Переносится
почти дословно.

3.2. **База данных** (`database`): интерфейс `laplace:lapp/database` — `execute`, `query`,
`query-row` над `variant value { null, integer(s64), real(f64), text(string), blob(list<u8>) }`;
хост — `rusqlite` (feature `bundled`, чтобы собиралось под Android), путь из `[database]`, соединение
на инстанс. Перенос логики `wasm_interop/database.rs`.

3.3. **Исходящий HTTP** (`http`): предпочтительно стандартный `wasi:http` через
`wasmtime-wasi-http` с проверкой метода, хоста и таймаута из `network.http` в
`WasiHttpView::send_request`; альтернатива — свой импорт поверх `reqwest`, как в старом. Готово:
запрос к неразрешённому хосту получает ошибку, к разрешённому — ответ.

3.4. **`sleep`**: в WASI p2 часы и `poll` доступны всегда; решить — убрать разрешение или не
линковать `wasi:clocks` без него.

## Этап 4. Push между front и back (замена WebSocket)

4.1. **Хост.** Импорт `client.send(message)` → событие Tauri в окно лаппа (`emit_to(label, ...)`)
или `tauri::ipc::Channel`, который фронт открывает командой `subscribe`; экспорт
`on-client-message(message)` для потока front → back. Разрешение `websocket`.

4.2. **Фронт.** В `laplace-front-api` — подписка на сообщения; для htmx — расширение по образцу
`client-router`, которое вставляет присланные back-ом фрагменты (аналог htmx-ws).

## Этап 5. P2P

5.1. Перенести `GossipsubService` на актуальный libp2p как сервис хоста на лапп (tokio): импорт
`p2p` (`dial`, `add-address`, `publish`, `close`), экспорт `on-p2p-message`, ответы на операции — как
`MessageIn::Response` в старом. Разрешение `tcp`, настройки `network.gossipsub`, глобальный
`p2p.mdns_discovery_enabled`.

5.2. Ключ пира хранить на хосте в каталоге данных лаппа, а не присылать с клиента (в старом
keypair генерировался в браузере и передавался в `/api/p2p`).

5.3. Android: mDNS требует `WifiManager.MulticastLock` и разрешение
`CHANGE_WIFI_MULTICAST_STATE` — через JNI, по образцу `android.rs`.

## Этап 6. Лаунчер

Макет — `laplace-new-old/laplace-front/src/app.rs`, поведение — `laplace_client`. Компоненты wingy,
действия через htmx + client-router, вызовы — команды этапа 1.

6.1. Список из `get_lapps` вместо захардкоженного.
6.2. Переключатель «включён», чекбокс «автозагрузка», разрешения — чипы требуемых с отметкой
выданных; каждое изменение → `update_lapp`, строка лаппа перерисовывается по ответу.
6.3. Показ ошибок (тосты/callout): ошибки команд и ответов back-ов.
6.4. Локализация: словари en/ru (перенести из `laplace-new-old/laplace-front/locales`), начальный
язык из `get_lang`, меню смены языка; при желании — сохранение выбора в `Laplace.toml`.
6.5. Меню/боковая панель с пунктом «Добавить лапп» (этап 7).
6.6. Индикатор «запущен» и кнопка остановки (команда `stop_lapp`) — из старого TODO.

## Этап 7. Установка лаппов

7.1. **Формат `.lar`**: zip с `config.toml`, `back/<name>-back.wasm` (необязательно), `front/**`;
имя — из имени файла (как в старом) или из манифеста. Записать формат в `docs/`.
7.2. **Команда `add_lapp`**: выбор файла через `tauri-plugin-dialog` (на Android — SAF URI, чтение
через `tauri-plugin-fs`), распаковка в оба корня с защитой от zip-slip, отказ, если лапп есть,
регистрация в реестре без перезапуска (ассеты и так читаются с диска).
7.3. **`remove_lapp`** с подтверждением; каталог данных лаппа по умолчанию сохраняется.
7.4. Задача `cargo make lar` (`APP_NAME=...`), собирающая архив примера.

## Этап 8. Примеры

Каждый пример — `examples/<name>/{back,front,common?,config.toml}`, фронт на hypertext + wingy +
htmx, back на SDK этапа 2.6; задачи в `Makefile.toml` по образцу `echo`.

8.1. echo — расширить (метод, заголовки, тело), это эталон для документации.
8.2. todo — SQLite (этап 3.2): список, добавление, отметка, удаление, очистка выполненных.
8.3. notes — markdown-файлы в каталоге данных (этап 3.1): список с превью (`make_preview` из
`notes_common`), просмотр, правка, переименование, удаление; рендер markdown во фронте
(`pulldown-cmark`).
8.4. chat — push (этап 4) и gossipsub (этап 5): вход с ключом, добавление пира/адреса, сообщения.

## Этап 9. Тесты, документация

9.1. Юнит-тесты: разбор манифестов и `Laplace.toml`, `UpdateQuery`, проверка разрешений,
распаковка `.lar`.
9.2. Интеграционные тесты хоста на собранных примерах: echo, todo с временной БД, notes с временным
каталогом, отказ без разрешения, таймаут.
9.3. Тесты команд на mock-рантайме Tauri: ACL по окнам, `update_lapp` пишет `config.toml`.
Старые HTTP-тесты доступа (`tests/tests/main_access.rs`) заменяются этими.
9.4. README по структуре из `NOTES.md`, CHANGELOG заново, актуализация `docs/` и `AGENTS.md`.
