Этап 2.1 плана миграции (`26-10-01 migration plan.md`).

Сейчас `LappsManager::instance` (`crates/app/src/lapps.rs`) при каждом запуске инстанса вызывает `LappState::load`. Тот читает `<name>-back.wasm` с диска, компилирует его (`Component::from_file`), заново строит `Linker` с WASI и инстанцирует мир (`Http::instantiate`). Запуск теперь частый: back останавливается при выключении лаппа и при смене прав (`update_lapp`), а после 2.2 будет останавливаться и при trap. Каждый раз компонент компилируется заново, и первый запрос после перезапуска ждёт всю компиляцию.

Что сделать:

- **Компонент — один раз на лапп.** `Lapp` хранит скомпилированный `Component`. Он получается при первом запуске под той же блокировкой инстанса этого лаппа, чтобы компиляция одного лаппа не задерживала другие. Новый инстанс — это новый `Store` и инстанцирование уже скомпилированного компонента. Ошибка компиляции не кэшируется: следующий запрос попробует снова.
- **`Linker` и `InstancePre`.** `Linker` с WASI строится один раз в `LappsManager` (`Engine` там уже общий). Инстанс создаётся из `InstancePre` через `HttpPre`, который генерирует `bindgen!`. На этапе 3 состав импортов будет зависеть от прав лаппа: без права линкуется заглушка. Значит, `InstancePre` придётся пересобирать при смене прав, а `Component` останется прежним. Устроить хранение так, чтобы это не потребовало переделки: например, `Component` на лапп, а `InstancePre` — вместе с ним, со сбросом при смене прав.
- **Сброс при замене файла.** На этапе 7 обновление заменяет `<name>-back.wasm`. Сброс кэша при обновлении записать в пункт 7.3 плана, сейчас ничего не делать.
- **`LappState::load(engine, path, name)`** перестаёт читать файл сам. Остаётся создание инстанса из готового `InstancePre`, а чтение и компиляция переходят к `Lapp`.
- Отдельный поток-исполнитель с очередью на лапп не делать (обоснование — в плане, 2.1).

Готово, когда:

- тест в `crates/app/tests/lapps.rs`: echo отвечает на запрос, затем `echo-back.wasm` удаляется из временного корня, back останавливается (`update_lapp` с выключением и включением), и следующий запрос снова получает ответ — компонент не читается с диска повторно;
- остальные тесты реестра проходят без изменений по смыслу;
- `cargo make lint` и `cargo make test` проходят.

---

Сделано:

- `LappsManager` строит `Linker` с WASI один раз (`LappsManager::new`, вместо `Default`).
- `Lapp::compiled` — `Mutex<Option<HttpPre<WasiStates>>>`: компиляция и линковка при первом
  запуске, под блокировкой инстанса этого лаппа; ошибка не запоминается. `Component` отдельно не
  хранится — при пересборке `InstancePre` на этапе 3 он берётся из `HttpPre::instance_pre().component()`.
- `LappState::load` убран, `LappState::new(engine, name, &pre)` только инстанцирует.
- Тест `restarted_backend_is_not_compiled_again`.
- План, пункт 7.3: при обновлении сбрасывать скомпилированный back; `docs/architecture.md`, «Реестр
  лаппов».

`cargo make lint` и `cargo make test` проходят.
