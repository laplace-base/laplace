Этап 3.3 плана миграции (`26-10-01 migration plan.md`). Опирается на контекст инстанса (`InstanceContext`, 3.1; хосты back-а добавить в него здесь) и на способ отказа без права, выбранный в 3.2.

Сейчас back не может сделать ни одного сетевого запроса. При этом настройки уже есть:
- манифест просит хосты, методы и тайм-аут — `[required.network.http.back]` (`BackHttpSettings`);
- пользователь выбирает хосты — `[allowed.network.http.back]`;
- действующие хосты считает `LappUserSettings::effective_http_hosts().back`, с учётом права `http` back-а.

Back — место для запросов с сессией и cookie и к сайтам без CORS: у фронта cookie внешних сайтов общие для всех лаппов, а CORS режет ответы (`docs/architecture.md`, «Внешние запросы фронта»).

Что сделать:

- **Протокол — `wasi:http`.** Стандартный `wasi:http/outgoing-handler` через `wasmtime-wasi-http` (версия в пару к `wasmtime` 49), а не свой импорт поверх `reqwest`, как в старом. Причины:
  - back собирается под `wasm32-wasip2`, где `wasi:http` — часть платформы;
  - для клиента в SDK есть готовые привязки (`wasip2` уже в `Cargo.lock`);
  - проверку можно встроить в `WasiHttpView::send_request`.

  Своего интерфейса в `wit/` не добавляется. Записать решение в план, убрав его из «открытых решений».
- **Хост.**
  - `wasmtime_wasi_http::add_only_http_to_linker_sync` в общий `Linker`.
  - `WasiStates` реализует `WasiHttpView`: свой `WasiHttpCtx` и `ResourceTable`, общий с WASI.
  - `send_request` перед отправкой проверяет:
    - право `http` back-а по контексту инстанса;
    - хост запроса по действующим хостам: точное имя, `*.` — поддомены, `all`. Порт — частью хоста, как в CSP фронта;
    - метод по `required.network.http.back.methods`;
    - схему: `https`, а `http` — только для явно указанного хоста.

    Отказ — `ErrorCode::HttpRequestDenied`.
  - Тайм-ауты — из `timeout_ms` манифеста (`OutgoingRequestConfig`: соединение, первый байт, между байтами). Дедлайн по эпохам блокирующее ожидание сети не прерывает (26-11-15), так что тайм-аут запроса обязателен.
- **Локальная сеть.** Запросы к loopback, частным и link-local адресам (`127.0.0.0/8`, `::1`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `fc00::/7`, `fe80::/10`) и к `localhost` — только если хост указан в списке явно, а не через `all` или `*.`. Хост-литерал IP проверяется сразу. Имя, которое разрешается в частный адрес (DNS rebinding), — проверить, даёт ли `wasmtime-wasi-http` подменить резолв или соединение. Если нет — записать ограничение в `docs/architecture.md` и в план.
- **`HttpMethod`** (`crates/settings/src/lapp.rs`) знает только `get`/`post` — дополнить `put`, `delete`, `patch`, `head`, `options`. Разбор манифеста с ними — тест.
- **SDK.** `laplace_back_api::http_client::send(http::Request<Vec<u8>>) -> Result<http::Response<Vec<u8>>, Error>` поверх `wasi:http` (через крейт `wasip2` или свои привязки в `generate!`), с ошибкой, по которой видно отказ хоста. Блокирующий вызов, без async.
- **Тестовый сервер.** Тесты не ходят в интернет. Локальный HTTP-сервер в тесте на `127.0.0.1` со случайным портом (`std::net::TcpListener` с ручным ответом, без новых зависимостей) — он же проверяет правило про loopback: разрешён только при явном `127.0.0.1:<port>` в хостах.
- **Документация.** `docs/architecture.md` (возможности back-а, внешние запросы), `docs/domain.md` (право `http` back-а), план (3.3), `AGENTS.md` при необходимости.

---

 Все четыре правки имеют смысл. Но вторая и четвёртая — по сути одна, а третья уже наполовину работает. Предлагаю такое решение.

 1. Методы для каждого хоста — стоит сделать

 Сейчас  methods  один на всю секцию  [required.network.http.back] . Предлагаю, чтобы запись хоста была либо строкой, как сейчас, либо таблицей со своими методами. Общий  methods  остаётся значением по
 умолчанию:

 
   [required.network.http.back]
   methods = ["get"]                     # для записей без своих методов
   hosts = [
     "api.example.org",
     { host = "upload.example.org", methods = ["post", "put"] },
   ]
 

   • Какая запись решает. Методы берутся из самой близкой записи: явный хост, затем маска с более длинным доменом, затем  all . Это то же правило, что мы только что ввели для  Exact / Broad , только с порядком
     и между масками.
   • Кто задаёт методы. Только автор: он знает, какой API нужен лаппу. Пользователь выбирает хосты, расширить методы он не может.
   • Фронт. Там методы ограничить нельзя, CSP этого не умеет. Поэтому для  network.http.front  запись с  methods  должна быть ошибкой разбора манифеста, а не тихо игнорироваться.

 3. Пользователь шире манифеста — работает, но не полностью

 Если в манифесте  hosts = "all" , пользователь уже может перечислить любые свои хосты:  allowed_by  раскрывает  all  манифеста в список пользователя. Для лаппа под адрес, который знает только пользователь
 (клиент своего сервера, RSS-читалка), этого хватает. Нужно только, чтобы лаунчер в этом случае спрашивал у пользователя список, а не выдавал  all .

 Не хватает другого случая: у автора есть свои хосты, и пользователь должен иметь возможность добавить к ним ещё. Разрешать пользователю всегда выходить за манифест я бы не стал: тогда манифест перестаёт что-
 либо значить. Лучше явная отметка автора:

 
   [required.network.http.back]
   hosts = ["api.example.org"]
   user_hosts = true      # пользователь может добавить хосты, которых нет в списке
 

 Добавленные пользователем хосты получают методы по умолчанию из манифеста. То же правило подходит и фронту: там добавленный хост просто попадёт в CSP.

 2 и 4. Локальная сеть и подсети — одна правка

 «Разрешить локальные адреса через  all  или  *. » — это частный случай «разрешить подсеть». Предлагаю новый вид записи  network : адреса по CIDR или ключевое слово  lan  (все частные, link-local и ULA-
 диапазоны). Тогда пользователь, который хочет « all  плюс локальная сеть», просто добавляет запись  lan . Отдельный флаг не нужен.

 
   # манифест: лаппу нужна локальная сеть пользователя, а какая — автор не знает
   hosts = [{ network = "lan", ports = [80, 8080], methods = ["get"] }]
 
   # решение пользователя: только своя подсеть
   hosts = [{ network = "192.168.1.0/24" }]
 

   • Кто сужает. Пользователь может сузить  lan  до конкретной подсети. Расширить сеть сам он не может: это уже решение уровня  user_hosts .
   • Только по IP-адресам. Запись  network  совпадает только с IP в URL. Через имена разрешать её не стоит: это тот же DNS rebinding, только в обратную сторону. Лапп, который ищет устройства, и так работает с
     адресами.
   • Loopback ( 127.0.0.0/8 ,  ::1 ) — это сервисы самого устройства, они чувствительнее домашней сети. Предлагаю не включать его в  lan . Его можно разрешить только явной записью:  127.0.0.1:8080  или  { netwo
     rk = "127.0.0.0/8" } .
   • Только back. CIDR в CSP не выразить, поэтому  network  у фронта — ошибка разбора манифеста.
   • Поиск устройств — это не только HTTP. mDNS и сканирование портов — это UDP и TCP, то есть этап 5 (право  tcp , P2P). Запись  network  покрывает только устройства с веб-интерфейсом.

 Что ещё затронет

   • Лаунчер (этап 6) должен показывать, что выдаётся: «любые хосты, которые вы укажете», «локальная сеть» — простым текстом, а не CIDR.
   • В  UpdateQuery  придётся добавить выдачу и отзыв записей хостов: этот пункт уже есть в плане (6.2).
   • Структура  HttpHosts  из  "all" | [строки]  превращается в список записей трёх видов:  host , маска,  network . Чтобы не ломать формат,  "all"  и строки пусть разбираются как раньше.
