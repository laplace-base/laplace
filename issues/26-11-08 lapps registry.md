Этап 1.4 плана миграции (`26-10-01 migration plan.md`). Зависит от 1.1 (раскладка), 1.2 (схема манифеста) и 1.3 (чтение манифеста и решений пользователя).

Сейчас `LappsManager::load_lapps` грузит все back-и при старте в `HashMap<String, Mutex<LappState>>` (`State::lapps`), а манифесты не читаются: `enabled` и разрешения проверять нечем, и ни один лапп нельзя выключить.

Что сделать:

- **Состав реестра.** Реестр хранит для каждого лаппа манифест (`lapps/back/<name>/manifest.toml`) и решения пользователя (`lapps/config/<name>.toml` или значения по умолчанию, если файла нет). Отдельно от реестра — `HashMap<String, Mutex<LappState>>` работающих инстансов. Фильтр `lapps.allowed` из `Laplace.toml` применяется к реестру, как сейчас к загрузке.
- **Ошибки чтения.**
  - Нечитаемый манифест — лапп пропускается с ошибкой в логе (поведение 0.1); в старом `laplace` манифест тоже был обязателен.
  - Нечитаемый файл решений пользователя — лапп пропускается с ошибкой в логе. Значения по умолчанию не подставляются: иначе следующий `update_lapp` перезапишет файл пользователя.
- **Запуск инстансов.** При старте инстанциируются только лаппы, для которых `is_lapp_startup_active()`. Остальные — лениво при первом `handle_http`: `LappState::load` из `lapps/back/<name>/`, инстанс кладётся в мапу и переиспользуется.
- **Проверки перед вызовом back-а** — аналог `check_enabled_and_allow_permissions` старого:
  - `!enabled` → ошибка «lapp not enabled»;
  - если `invoke_back` в действующих правах нет → «permission denied».

  Ошибки уходят во фронт, как после 0.1.
- **Лапп без back-а** (манифест есть, `<name>-back.wasm` нет): запрос к нему — понятная ошибка, а не неудача инстанцирования.
- **`LappState::load` не читает настроек.** Манифест и решения пользователя берутся только из реестра. На этапе 3 по действующим правам будут решать, какие импорты линковать.
- **Лаунчер** (`MAIN_NAME`) в реестре есть: его манифест нужен для ACL (1.6) и ассетов (1.7). Инстанс для него не создаётся, и `handle_http` из его окна получает ошибку «нет back-а», как любой лапп без back-а.

Ленивая загрузка меняет конкурентность. Сейчас `State::lapps` — неизменяемая мапа `Mutex`-ов, а `process_http` вызывается из `spawn_blocking` параллельно для разных лаппов. Добавлять инстансы на лету можно, только если сама мапа под блокировкой: `RwLock`/`Mutex` поверх `HashMap` или ленивая ячейка на каждый лапп, заведённая заранее по реестру. Компиляция компонента не должна идти под блокировкой, общей для всех лаппов, иначе первый запрос к одному лаппу задержит все остальные.

Тестам в `crates/app/tests/` (хелпер `state_with`) понадобятся лаппы с разными манифестами и решениями пользователя. Решить, как их получить:

- фикстуры: временные корни с `manifest.toml`, `lapps/config/<name>.toml` и скопированным собранным `echo-back.wasm`;
- или второй минимальный пример-заглушка.

Готово, когда тесты проходят:

- выключенный лапп отвечает ошибкой;
- лапп без `autoload` поднимается на первом запросе;
- лапп без файла решений пользователя работает со значениями по умолчанию;
- лапп без back-а получает ошибку «нет back-а»;
- если `invoke_back` явный — лапп без него получает отказ в разрешении.
