Сейчас на Android, в отличии от десктопной версии, lapp открывается в том же окне, что и браузер приложений (фронтэнд laplace), а не в новом окне. Необходмо сделать так, чтобы lapps открывались на мобильном в новых окнах (новых activity?) чтобы их можно было просматривать и выбирать из экрана недавних приложений. При этом главное приложение и окно laplace должно оставаться рабочим, чтобы также оставалось рабочим и дочернее открытое lapp. Каким образом это осуществимо?

● Пока пересобирается APK — как это устроено.

  Модель Tauri/tao на Android: окно = Activity. tao 0.35 умеет несколько activity в одном процессе (AndroidContext::create_activity → WryActivity.startActivity(cls), id окна = id activity), а Tauri 2.11
  пробрасывает это в WebviewWindowBuilder::activity_name(class) (только под cfg(android)). Сейчас open_lapp его не задаёт, поэтому tao берёт «следующую свободную» activity — ту же, где уже живёт лаунчер, и lapp
  подменяет собой его webview.

  Что сделано:

  1. LaplaceActivity.kt (новый) — абстрактная база с общей настройкой окна (edge-to-edge + отступы по insets из прошлой задачи).
  2. MainActivity.kt — теперь просто class MainActivity : LaplaceActivity().
  3. LappActivity.kt (новый) — class LappActivity : LaplaceActivity(). Класс обязан лежать в org.laplace: tao ищет его через getAppClass("org.laplace.$activity_name"), а обратно имя берёт из
     getLocalClassName().
  4. AndroidManifest.xml — объявление:
  <activity
      android:name=".LappActivity"
      android:documentLaunchMode="always"
      android:autoRemoveFromRecents="true"
      android:taskAffinity="${applicationId}.lapp"
      ... />
     documentLaunchMode="always" — ключевой пункт для твоего требования: экран «недавних» показывает задачи, а не activity, поэтому без него все lapp'ы сложились бы стопкой в задаче лаунчера. С ним каждый
     запуск создаёт отдельную document-задачу → отдельная карточка в recents; autoRemoveFromRecents убирает карточку, когда окно закрыто.
  1. crates/app/src/api/laplace.rs — open_lapp строит окно и добавляет
  #[cfg(target_os = "android")]
  let builder = builder.activity_name(LAPP_ACTIVITY);
     Один класс на все lapp'ы: documentLaunchMode="always" создаёт новый экземпляр и новую задачу на каждый запуск, так что пул классов не нужен и число одновременно открытых lapp'ов ничем не ограничено.

  Главное окно при этом остаётся живым: процесс, event loop и LappsManager одни на всё приложение, MainActivity — singleTask в своей задаче, handle_http по-прежнему различает окна по label (= имени лаппа), а не
  по activity.

  Известное ограничение получившегося: карточка в recents подписана @string/main_activity_title («laplace») для всех lapp'ов — заголовок задачи берётся из android:label, а не из содержимого. Различать их можно
  по превью. Если нужно имя лаппа на карточке, это setTaskDescription(ActivityManager.TaskDescription(name)) внутри LappActivity, но имя туда сначала надо как-то передать — tao в интенте передаёт только id
  окна, так что понадобится либо чтение webView.title после загрузки, либо свой JNI-вызов из Rust. Могу доделать отдельно, если нужно.

Следует учесть, что lapp'ы будут настраиваться пользователем динамически, он их может удалять и добавлять в процессе эксплуатации программы. Таким образом, их число явно не должно быть прописано или ограничено статической конфигурацией приложения.

● Ключевой момент: в текущей реализации ничего пер-лапп в статической конфигурации нет. Проверю только один сценарий, который динамика делает вероятным.
● Учтено — и в текущей реализации это уже так, кроме одного места, которое я сейчас закрыл.

  Почему статического ограничения нет. Классы activity в манифесте — это не «слоты под лаппы», а типы окон. Их ровно два и они не зависят от набора лаппов: MainActivity (лаунчер) и LappActivity (любое окно
  лаппа). Все открытые лаппы — экземпляры одного и того же LappActivity, создаваемые на лету:
  
  - open_lapp передаёт в WebviewWindowBuilder::activity_name имя класса, а не имя лаппа;
  - tao на каждый вызов делает startActivity(LappActivity::class) с новым случайным id окна и кладёт контекст в CONTEXTS по этому id — имена классов там не обязаны быть уникальными;
  - android:documentLaunchMode="always" заставляет систему создавать новый экземпляр в новой задаче на каждый запуск.
  
  Поэтому число одновременно открытых лаппов ничем не задано, добавление/удаление лаппа не требует ни правки манифеста, ни пересборки APK, ни пула заранее объявленных классов (альтернатива с LappActivity1..N
  как раз и вводила бы жёсткий потолок — я её не использовал именно поэтому).
  
  Что поправил. Динамическая эксплуатация делает вероятным повторный тап по уже открытому лаппу, а метка окна в Tauri — это имя лаппа (по ней handle_http находит бэкенд), и второе окно с той же меткой создать
  нельзя: build() возвращал ошибку, а .expect("Failed to open lapp") ронял бы команду. Теперь open_lapp сначала проверяет:
  
  if let Some(window) = handle.get_webview_window(name) {
      log::debug!("Lapp '{name}' is already open");
      if let Err(err) = window.set_focus() { ... }
      return;
  }   
  
  На десктопе это поднимает существующее окно; на Android set_focus в tao — заглушка (warn!("set_focus not yet implemented on Android")), так что окно просто останется открытым, переключиться на него можно
  через recents. Чтобы поднимать задачу лаппа на передний план программно, понадобится свой JNI-вызов (ActivityManager.AppTask.moveToFront) — это уже отдельная задача, скажи, если нужна.
  
  Два системных потолка, о которых стоит знать (оба — свойства Android, не нашей конфигурации):
  
  1. android:maxRecents для document-activity по умолчанию 16: когда открыто больше, система выкидывает самую давнюю задачу лаппа из recents и убивает её activity. Поднимается атрибутом в манифесте до 50
     (системный максимум). Сейчас стоит значение по умолчанию — скажи, если хочешь 50.
  2. Все окна живут в одном процессе: при нехватке памяти система убьёт процесс целиком, вместе с лаунчером и всеми лаппами.
  
  Проверки: cargo make lint и cargo check -p laplace-app --target aarch64-linux-android проходят. APK с этой правкой не пересобирал (менялся только Rust) и на устройстве по-прежнему ничего не проверял.
